# UTMMonitor


> **Статус проекта: портфолио.**
>
> UTMMonitor опубликован в демонстрационных целях как пример разработки Windows-приложения на Python. Репозиторий предназначен для ознакомления с архитектурой проекта, реализацией фоновых обработчиков, парсингом логов ЕГАИС УТМ, локальным хранением данных и автоматическим обновлением.
>
> Проект не позиционируется как готовое к самостоятельному развёртыванию решение. Для полноценной работы требуются соответствующая инфраструктура, конфигурация, оборудование и доступ к серверным компонентам. Работоспособность публичной копии в произвольном окружении не гарантируется.


**UTMMonitor** — фоновое Windows-приложение для мониторинга ЕГАИС УТМ, сбора алкогольных чеков, контроля марок и количественных остатков магазина.

Программа предназначена для круглосуточной работы на компьютерах магазинов, подключённых к ЕГАИС. Она собирает данные из логов УТМ, хранит их локально, взаимодействует с Рутокеном, контролирует состояние УТМ и синхронизирует данные с сервером.

Приложение работает в фоновом режиме, автоматически обновляется и восстанавливает автозапуск при его случайном отключении.

## Возможности

### 1. Сбор и обработка чеков

UTMMonitor извлекает информацию о продажах алкогольной продукции из логов ЕГАИС УТМ.

Поддерживаемые источники:

- Текущий лог `transport_info.log`.
- Архивы логов `transport_info*.log.gz`.
- Данные из логов программы «Декларант» — в качестве дополнительного источника, если в логах УТМ отсутствуют данные о чеках за последнюю неделю.

Из логов извлекаются следующие сведения:

- дата и время операции;
- тип чека — продажа или возврат;
- марки алкогольной продукции;
- цена продажи;
- объём бутылки, если он указан в данных продажи.

Обработанные чеки сохраняются в локальную базу данных. Повторное сохранение уже известных чеков исключается.

После успешной отправки на сервер чек получает статус отправленного. Записи старше 90 дней автоматически удаляются.

### 2. Мониторинг ЕГАИС УТМ

Программа контролирует состояние ЕГАИС УТМ и поддерживает его работоспособность.

Основные функции:

- проверка состояния службы `UTM Transport`;
- автоматический запуск службы, если она не работает;
- периодическая проверка состояния УТМ;
- определение порта, на котором работает УТМ;
- получение версии установленного УТМ;
- мониторинг входящих документов ЕГАИС;
- обработка документов с ошибками, возникающими при слишком частых запросах количественных остатков.

Мониторинг входящих документов выполняется с коротким интервалом, чтобы успеть получить необходимые сведения до того, как документы будут обработаны другими программами.

UTMMonitor не удаляет входящие документы в рамках стандартного мониторинга: их обработка остаётся за штатными программами. Исключение — отдельная очистка ошибочных документов, связанных с частыми запросами остатков.

### 3. Контроль алкогольных марок

Программа поддерживает несколько механизмов проверки марок:

- получение с сервера предполагаемого перечня марок, находящихся на остатках магазина;
- проверка марок по файлу, размещённому на сервере, если такой файл доступен;
- массовая асинхронная проверка помарочных остатков в ЕГАИС;
- передача собранных сведений на сервер для дальнейшего сопоставления и анализа.

Для проверки используются сведения, полученные из ЕГАИС, и данные серверной инфраструктуры.

### 4. Количественные остатки

UTMMonitor получает сведения о количественных остатках алкогольной продукции в ЕГАИС и передаёт их на сервер.

Программа учитывает, что запросы остатков могут выполняться другими приложениями. Поэтому перед собственным запросом проверяется наличие более свежего запроса за текущий час, чтобы не создавать лишнюю нагрузку на УТМ.

Дополнительно выполняются:

- мониторинг входящих документов, связанных с остатками;
- проверка заданий на отправку данных со стороны сервера;
- обработка ошибочных документов, возникающих из-за слишком частых запросов остатков.

### 5. Работа с Рутокеном и сертификатами

Для взаимодействия с Рутокеном используется библиотека `rtpkcs11ecp.dll` и собственные классы на базе `ctypes`.

Получаемые сведения используются для идентификации магазина и контроля состояния оборудования.

Программа получает или проверяет:

- ИНН и КПП магазина;
- идентификатор ЕГАИС;
- сведения о сертификатах RSA и ГОСТ и сроках их действия;
- версию программного обеспечения Рутокена;
- наличие подключённого токена;
- доступную память токена;
- необходимость обновления сведений о сертификатах и подключения к ним.

На основе этих данных обновляются настройки текущего магазина.

### 6. Фоновая работа и администрирование

Программа рассчитана на автономную работу без постоянного участия пользователя.

Возможности:

- запуск в фоновом режиме без основного пользовательского окна и уведомлений;
- защита от повторного запуска с помощью системного Mutex;
- проверка автозапуска Windows и его восстановление при отключении;
- получение AnyDesk ID, если AnyDesk доступен;
- обновление настроек магазина;
- автоматическое обновление приложения с сервера;
- отправка диагностических логов по запросу сервера;
- повторные попытки отправки данных при временных сетевых ошибках.

По запросу сервера программа собирает собственные логи и логи ЕГАИС УТМ в ZIP-архив для диагностики.

## Архитектура

Приложение состоит из основного потока и нескольких независимых фоновых обработчиков. Каждый обработчик отвечает за отдельную задачу и выполняет собственный цикл работы.

```text
UTMMonitor
│
├── Основной поток
│   ├── Инициализация логирования
│   ├── Обработка завершения программы
│   ├── Защита от повторного запуска
│   ├── Проверка обновлений
│   ├── Инициализация ConfigManager
│   └── Идентификация и настройка магазина
│
├── VersionWorker
│   └── Проверка версий и автообновление
│
├── EgaisRunnerWorker
│   └── Контроль запуска ЕГАИС УТМ
│
├── ChequeWorker
│   └── Разбор логов и обработка чеков
│
├── LogWorker
│   └── Сбор и отправка диагностических логов
│
├── MarkWorker
│   └── Проверка марок по файлам с сервера
│
├── EgaisDocWorker
│   └── Мониторинг входящих документов ЕГАИС
│
├── EgaisRestWorker
│   └── Количественные остатки
│
└── AmcWorker
    └── Асинхронная проверка помарочных остатков
```

### Основной поток

При запуске программа последовательно выполняет следующие действия:

1. Инициализирует логгер.
2. Регистрирует обработчики сигналов завершения.
3. Проверяет, не запущен ли уже другой экземпляр приложения. Для защиты от двойного запуска используется Mutex.
4. Выполняет первичную проверку версии и при необходимости запускает процедуру обновления.
5. Инициализирует `ConfigManager`.
6. Создаёт или читает `config.ini`, проверяет автозапуск, обновляет сведения об УТМ и общие настройки магазина.
7. Получает AnyDesk ID и сведения о Рутокене, сертификатах и идентификаторах магазина.
8. Проверяет, не находится ли ИНН магазина в списке `DISABLED_INN`. Если находится, отключает автозапуск и завершает работу.
9. Запускает фоновые обработчики.

После инициализации обработчики работают независимо друг от друга.

## Фоновые обработчики

| Обработчик | Назначение | Периодичность |
|---|---|---|
| `VersionWorker` | Проверка новой версии и автообновление | При запуске и далее каждые 30 минут |
| `EgaisRunnerWorker` | Проверка и запуск службы UTM Transport | Каждые 30 минут |
| `ChequeWorker` | Разбор логов и сохранение новых чеков | Каждые 10 секунд |
| `ChequeWorker` | Проверка чеков из логов «Декларанта» | Каждые 6 часов |
| `LogWorker` | Проверка команд сервера | Каждые 5 минут |
| `LogWorker` | Отправка краткого лога за текущий день | Раз в час |
| `MarkWorker` | Проверка команд сервера и файлов с марками | Каждые 5 минут |
| `EgaisDocWorker` | Мониторинг входящих документов | Каждые 3 секунды |
| `EgaisDocWorker` | Проверка заданий на отправку документов от сервера | Каждые 5 минут |
| `EgaisRestWorker` | Мониторинг документов по количественным остаткам | Каждые 3 секунды |
| `EgaisRestWorker` | Проверка заданий сервера | Каждые 5 минут |
| `EgaisRestWorker` | Запрос количественных остатков | Не чаще одного раза в час при отсутствии более свежего запроса |
| `AmcWorker` | Массовая асинхронная проверка марок | Первый запуск через 10 минут, далее каждые 20 минут |
| `AmcWorker` | Проверка заданий на отправку данных | Каждые 5 минут |

Указаны основные циклы работы. Внутренние операции, обработка ошибок и ожидание ответов могут выполняться дополнительно.

### Повторные попытки

Для предусмотренных отправок на сервер реализованы повторные попытки. Если отправка не удалась, обработчик повторяет её в следующем цикле.

Это позволяет переживать временную недоступность сети или сервера без необходимости вручную перезапускать приложение.

## Локальные базы данных

Для хранения данных используются отдельные базы SQLite.

| Файл | Назначение |
|---|---|
| `cheque.db` | Чеки, информация об их обработке и статусах отправки |
| `rests.db` | Данные, связанные с количественными остатками |
| `amc.db` | Данные, используемые при проверке помарочных остатков |

Базы данных автоматически создаются при первом обращении, если ещё не существуют.

Каждый обработчик использует собственную базу данных, когда это предусмотрено его логикой. Такое разделение уменьшает конкуренцию за доступ к данным между независимыми задачами.

### Обработка чеков

- Новые чеки сохраняются локально.
- Уже известные чеки повторно не добавляются.
- После успешной отправки обновляется статус чека.
- Записи старше 90 дней очищаются автоматически.

Локальное хранение позволяет сохранять состояние обработки между запусками приложения.

## Требования

### Совместимость

Приложение разработано для работы в Windows 7, Windows 8, Windows 8.1, Windows 10 и Windows 11, включая 32- и 64-разрядные системы.

В качестве целевой среды сборки выбран **Python 3.8 x86**. Это решение обусловлено необходимостью обеспечить совместимость со старыми версиями Windows и используемыми в рабочем окружении компонентами ЕГАИС.

Совместимость приложения проверена в реальных условиях эксплуатации на инфраструктуре более чем **150 магазинов**, использовавших различные версии и разрядности Windows: Windows 7, Windows 8, Windows 8.1, Windows 10 и Windows 11 (x86/x64).

Разрядность итогового приложения определяется используемым интерпретатором Python: сборка на Python x86 создаёт 32-разрядное приложение, которое может работать и в 64-разрядной Windows.

### Для запуска

- Windows 7, Windows 8, Windows 8.1, Windows 10 или Windows 11, x86 или x64.
- Настроенный ЕГАИС УТМ.
- Рутокен и соответствующие сертификаты, если они требуются для работы магазина.
- Доступ к серверу приложения.
- Права, необходимые для настройки автозапуска и взаимодействия с УТМ.

### Для разработки и сборки

- Python 3.8.
- Зависимости из `requirements.txt`.
- Inno Setup 6 для создания установщика.
- Файлы и библиотеки, необходимые приложению, включая `rtpkcs11ecp.dll`.
- `signtool` и сертификат для цифровой подписи, если требуется подписанная сборка.

Архитектура собранного приложения определяется используемым интерпретатором Python. Например, сборка через 32-разрядный Python создаёт 32-разрядное приложение.

## Настройка

Параметры приложения задаются через `.env` и `config.ini`.

### Файл `.env`

`.env` используется для конфигурационных параметров, которые должны задаваться отдельно от исходного кода, включая версию, адрес сервера и списки ИНН.

Пример `.env.example`:

```dotenv
# Версия приложения
VERSION=1.0.0

# Адрес сервера приложения
URL_SERVER=https://example.invalid

# Списки ИНН через запятую
VALID_INN=0000000000
DISABLED_INN=
```

Это демонстрационный пример. Перед запуском необходимо заполнить параметры в соответствии с используемой инфраструктурой.

Параметры сборки, такие как пути к Inno Setup, `signtool`, сертификату и сетевым каталогам публикации, следует хранить в локальном `.env` разработчика и не включать в конфигурацию готового приложения.

### Файл `config.ini`

`ConfigManager` создаёт или читает `config.ini` и обновляет настройки, необходимые для работы приложения и идентификации магазина.

Не редактируйте этот файл вручную без понимания назначения конкретных параметров.

## Запуск из исходников

### 1. Клонирование репозитория

```powershell
git clone <URL-РЕПОЗИТОРИЯ>
cd UTMMonitor
```

### 2. Создание виртуального окружения

```powershell
py -3.8 -m venv .venv
```

```powershell
python main.py
```

При запуске из исходников некоторые механизмы, связанные с исполняемым файлом, автозапуском и обновлением, могут вести себя иначе, чем в собранной версии. Для проверки полного цикла работы используйте сборку PyInstaller.

## Сборка приложения

Сборка выполняется скриптом `build.py` в каталоге `build`.

### Подготовка

1. Установите Python 3.8 нужной разрядности.
2. Установите зависимости из `requirements.txt`.
3. Установите Inno Setup 6, если нужен установщик.
4. При необходимости настройки цифровой подписи укажите локальные пути к `signtool` и сертификату.
5. Подготовьте локальный `.env` с параметрами сборки и публикации.

### Сборка

Перейдите в каталог сборки:

```powershell
cd build
```

Запустите сборку:

```powershell
python build.py
```

Скрипт выполняет следующие действия:

1. Проверяет версию приложения.
2. Подготавливает рабочий каталог.
3. Генерирует файл ресурсов версии `version.rc` и манифест `manifest.xml`.
4. Запускает PyInstaller с настройками `main.spec`.
5. Подготавливает пользовательский `.env`, исключая параметры сборки и публикации.
6. Создаёт ZIP-архив приложения.
7. Вычисляет MD5 архива и формирует `info.json`.
8. При наличии Inno Setup создаёт установщик.
9. При соответствующей настройке публикует сборочные артефакты на сервере.

### Дополнительные параметры

Подписать исполняемый файл перед упаковкой:

```powershell
python build.py --sign
```

Пропустить создание установщика:

```powershell
python build.py --no-installer
```

```text
build/work/output/
```

Ожидаемые артефакты:

```text
output/
├── UTMMonitor/
│   ├── UTMMonitor.exe
│   ├── .env
│   ├── lib/
│   └── scripts/
├── UTMMonitor.zip
├── info.json
└── UTMMonitor.exe
```

В данном примере `UTMMonitor.exe` внутри каталога `UTMMonitor/` — исполняемый файл приложения, а `UTMMonitor.exe` в корне `output/` — установщик Inno Setup.

Наличие установщика зависит от успешного завершения соответствующего этапа сборки.

## Автоматическое обновление

При запуске UTMMonitor проверяет наличие новой версии на сервере.

Если обновление доступно, программа загружает ZIP-архив, распаковывает его во временный каталог и запускает процедуру обновления.

Процесс обновления включает:

1. Подготовку новых файлов.
2. Завершение текущего экземпляра приложения.
3. Замену исполняемого файла и необходимых библиотек.
4. Запуск обновлённой версии.

После обновления программа запускается повторно. Локальные базы данных и пользовательские данные сохраняются.

Если новая версия не найдена, проверка продолжается в фоновом режиме каждые 30 минут.

## Безопасность

При подготовке публичного репозитория необходимо исключить конфиденциальные данные.

Не добавляйте в Git:

- `.env` с реальными настройками;
- сертификаты `*.pfx`, `*.p12` и приватные ключи;
- пароли сертификатов;
- внутренние адреса и сетевые пути серверов;
- рабочие конфигурации магазинов;
- логи с персональными или коммерчески чувствительными сведениями;
- готовые установщики, содержащие внутренние настройки, если они не предназначены для публичного распространения.

Рекомендуется добавить в `.gitignore`:

```gitignore
# Секреты и локальная конфигурация
.env
config.ini
*.pfx
*.p12
*.key

# Python
__pycache__/
*.py[cod]
.venv/

# Сборка
build/work/
dist/
*.spec.bak

# Локальные базы и логи
*.db
*.sqlite
*.sqlite3
*.log

# Локальная конфигурация
config.ini
```

Если конфиденциальные файлы уже были закоммичены, добавление их в `.gitignore` не удалит их из истории Git. В таком случае необходимо отдельно удалить их из истории и заменить скомпрометированные секреты.
